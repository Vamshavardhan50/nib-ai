Deployment

Nib ships as one static binary plus a model file and a tokenizer. The API needs a host that can execute binaries; the UI can live on any static host. This page covers the common paths.

What runs where

PieceNeedsGood hosts
Rust API + embedded UILinux/Windows/macOS process, 1 GB RAM for denseVPS, Docker, Render, Railway, Fly.io, Cloud Run
Static UI (index.html)Static file hosting onlyGitHub Pages, Netlify, Vercel, Cloudflare Pages
Documentation site (docs/)Static file hosting onlyGitHub Pages, Netlify, Vercel, Cloudflare Pages
Model files45 MB dense or 1 MB TurboBaked into the image or downloaded at startup
GitHub Pages cannot run Rust

Pages serves HTML, CSS, and JavaScript only. Host index.html and this docs site on Pages, but run nib serve on a separate host. Point the UI at it with ?api=https://your-api-host.

Get a public API URL — six steps

This is the short version. The HTTP API guide has the full endpoint walkthrough, tunnel instructions, UI connection, and troubleshooting.

1. Build

cargo build --release

2. Copy the three files

nib, nib.bin or turbo.bin, and tokenizer.json.

3. Run on 0.0.0.0

./nib serve --model nib.bin --tokenizer tokenizer.json --host 0.0.0.0 --port 8080

4. Terminate HTTPS

Use the platform's URL, or put Caddy/nginx in front of port 8080.

5. Test from outside

curl https://api.example.com/health
curl -X POST https://api.example.com/api/generate \
  -H "content-type: application/json" \
  -d '{"prompt":"ROMEO: ","length":40}'

6. Connect the UI

https://vamshavardhan50.github.io/nib-ai/?api=https://api.example.com
No public endpoint is included

The hosted UI and this documentation are static. They cannot execute Rust. Until you complete these steps, the only working endpoint is http://127.0.0.1:8080 on your own machine.

Build once

cargo build --release
# binary: target/release/nib
# model:  nib.bin (45.12 MB) or turbo.bin (994,656 bytes)
# vocab:  tokenizer.json

Copy those three files to the host and run:

./nib serve --model nib.bin --tokenizer tokenizer.json --host 0.0.0.0 --port 8080

Docker

The included multi-stage Dockerfile builds the release binary and copies a model into a slim Debian runtime.

# Fast, compact demo (default)
docker build -t nib-turbo .
docker run --rm -p 8080:8080 nib-turbo

# Real 90M dense model
docker build --build-arg MODEL=nib.bin -t nib-dense .
docker run --rm -p 8080:8080 --memory=1g nib-dense

The image exposes port 8080, runs as an unprivileged user, and reads HOST and PORT environment variables.

Docker Compose

services:
  nib:
    build:
      context: .
      args:
        MODEL: nib.bin
    ports:
      - "8080:8080"
    environment:
      HOST: 0.0.0.0
      PORT: 8080
    mem_limit: 1g
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:8080/health"]
      interval: 30s
      timeout: 5s
      retries: 3

The runtime image does not include curl by default. Add it to the Dockerfile or use a TCP check if you rely on Docker healthchecks.

VPS with systemd

# /etc/systemd/system/nib.service
[Unit]
Description=nib-rs language model API
After=network.target

[Service]
Type=simple
User=nib
WorkingDirectory=/opt/nib
ExecStart=/opt/nib/nib serve --model /opt/nib/nib.bin --tokenizer /opt/nib/tokenizer.json --host 127.0.0.1 --port 8080
Restart=on-failure
RestartSec=3
MemoryMax=1G

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now nib
curl http://127.0.0.1:8080/health

Caddy reverse proxy

api.example.com {
    reverse_proxy 127.0.0.1:8080 {
        transport http {
            read_timeout 300s
            write_timeout 300s
        }
    }
}

nginx reverse proxy

server {
    listen 443 ssl;
    server_name api.example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
        proxy_set_header Host $host;
    }
}

Render, Railway, Fly.io, Cloud Run

PlatformKey settings
RenderWeb Service → Docker → health check path /health → 1 GB RAM for dense → set PORT if required by the platform.
RailwayDeploy from the repo; Railway injects PORT; the Dockerfile CMD expands HOST and PORT.
Fly.iofly launch, internal port 8080, fly scale memory 1024, health check /health.
Google Cloud RunContainer port 8080, memory 1 GiB, request timeout 300 s, concurrency 1 (generation is serialized).

Dense generation can exceed default platform timeouts. Prefer Turbo for request/response services, or raise the timeout and cap length in your client.

Security

  • No built-in auth, TLS, or rate limiting. Put Nib behind a reverse proxy or platform gateway.
  • CORS is *. Any website can call a public instance. Restrict at the proxy or fork the header logic if the model is private.
  • Limit request size and rate. The server caps bodies at 64 KB and prompts at 4,096 characters, but it does not rate-limit clients.
  • Treat model files as trusted input. The loaders validate magic and dimensions, but they are not a sandbox for hostile files.
  • Run as an unprivileged user (the Dockerfile does) and keep the runtime image minimal.

CI

name: ci
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - run: cargo test --release
      - run: cargo build --release

The test suite uses tiny in-memory models, so CI does not need nib.bin or a network download.

Repository size

  • nib.bin is 45,117,066 bytes, under GitHub's 100 MB per-file limit. Normal Git works.
  • Each dense variant adds about 45 MB to history. Keep one shipped artifact; publish experiments as release assets.
  • turbo.bin is under 1 MB and is cheap to keep.
  • For files over 100 MB, use Git LFS or GitHub Releases. Do not rewrite history just to remove one model unless the size is a real problem.

Deployment checklist

  • Release binary built and tested on the target platform.
  • nib.bin or turbo.bin plus matching tokenizer.json copied.
  • /health returns {"status":"ok"}.
  • /api/info reports the expected model name, parameters, and file bytes.
  • Reverse proxy timeout at least 300 seconds for dense generation.
  • Memory limit at least 1 GB for dense, 128 MB for Turbo.
  • Static UI configured with ?api=https://your-api-host.
  • Authentication and rate limiting added at the proxy if the instance is public.
