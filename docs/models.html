Models & training

Four model families, one set of hand-written layers. This page explains the architectures, the exact parameter and file-size math, how the shipped 90M model was trained and pruned, and what the numbers do and do not mean.

CharLM

A character-level two-layer MLP. For a context of C characters, an embedding width E, hidden width H, and vocabulary V:

input ids (C) → embedding (C × E) → flatten (C·E)
→ Linear(C·E → H) → ReLU
→ Linear(H → V) → softmax → next character

Parameters:

P = V·E + C·E·H + H + H·V + V

The first term is the embedding table, the second is fc1, then its bias, then fc2 and its bias. The trainer uses cross-entropy loss and plain SGD with gradients averaged over the batch.

TurboLM

Turbo keeps the same 100M-entry shape but stores each large matrix as two thin factors: 

fc1: (C·E = 8192) × (H = 12114)  →  U(8192 × 30) · V(30 × 12114)
fc2: (H = 12114) × (V = 62)      →  U(12114 × 30) · V(30 × 62)

With V=62, E=128, C=64, H=12114, rank=30:

ItemCount
Logical dense parameters100,009,068
Stored factors, embedding, biases994,572
File after int8 quantization994,656 bytes
Compression vs f32 dense402×

The forward pass multiplies by the factors, so the logical shape is 100M while the number of independent stored weights is about 1M. This is why the file is under 1 MB. It is not a 100M-parameter dense model; it is a low-rank model of that shape.

Size math

Each dense matrix is stored as:

8-byte header (rows, cols)
rows × 4-byte f32 row scale
rows × ceil(cols / 2) packed 4-bit bytes

Biases are stored as a 4-byte length plus f32 values. The 32-byte file header records magic, version, vocabulary, embedding width, hidden width, context, and a reserved word.

header                 32 bytes
embedding matrix        4,224 bytes
fc1 matrix         44,687,368 bytes
fc2 matrix            381,578 bytes
fc1 bias               43,612 bytes
fc2 bias                  252 bytes
----------------------------------
total              45,117,066 bytes

At 4 bits per weight, the raw weights alone are about 45 MB; scales, headers, and f32 biases add roughly 80 KB. For comparison:

100B under 100 MB is impossible

Even at one bit per weight, 100B parameters need about 12.5 GB, before scales, embeddings, or runtime overhead. No quantization trick changes that information-theoretic floor. Nib targets 90M weights at 4 bits, which genuinely fits under 50 MB.

4-bit quantization

Dense weights are quantized row by row after training:

scale = max_abs(row) / 7
q     = round(weight / scale) clamped to -7..7
store q as a signed 4-bit nibble, two values per byte

One f32 scale per row preserves the dynamic range of each row without a per-weight scale. Biases remain f32. Loading dequantizes to f32, so inference runs on normal matrices; the 4-bit format is a storage format, not a low-precision compute kernel.

Pruning: 100M → 90M

A 100M dense model at 4 bits is 50,128,686 bytes, just over 50 MB. To land comfortably under 50 MB, the shipped model drops 1,212 hidden units:

  • Score every hidden unit by the L2 norm of its outgoing fc2 row.
  • Keep the 10,902 highest-scoring units, restoring their original order.
  • Copy the corresponding fc1 columns, fc1 bias entries, and fc2 rows.
  • Fine-tune the resulting sub-network on the same corpus.

The result is a direct sub-network with 90,004,008 independent weights. It is fully dense; pruning only chooses which hidden units survive.

The 62-token vocabulary contains newline, space, !&',-.:;?, uppercase letters, and lowercase letters. Everything is real text; no synthetic samples, no pre-trained weights, and no external model artifacts are used.

Training loss, not validation accuracy

The numbers below are mean cross-entropy on training windows. There is no held-out split, so they measure fit, not generalization. Treat generated samples as the practical quality check.

Training pipeline

Stage 1 — train Turbo from random weights

5 epochs, batch 32, SGD, lr 0.05, all 199,936 windows. Loss 2.3209 → 1.7765. Result: 994,656-byte turbo.bin.

Stage 2 — expand and fine-tune all 100M weights

Materialize W = U·V, then 2 epochs × 20,000 windows, batch 128, SGD, lr 0.02. Loss 1.5755 → 1.5290. Result: 50,128,686-byte dense artifact.

Stage 3 — prune to 90M and fine-tune

Keep 10,902 of 12,114 hidden units, then 3 epochs × 20,000 windows, batch 128, SGD, lr 0.01. Loss 1.5311 → 1.5154 (best epoch 1.5079). Result: 45,117,066-byte nib.bin.

Stage 4 — quantize and verify

Save each row as 4-bit nibbles with an f32 scale, reload, and compare predictions. The file is hashed and served through the same API as Turbo.

Reproduce the shipped model

./get-data.ps1
$bytes = [IO.File]::ReadAllBytes("shakespeare.txt")[0..199999]
[IO.File]::WriteAllBytes("shakespeare-200k.txt", $bytes)

nib turbo-train --input shakespeare-200k.txt --output turbo.bin \
  --tokenizer tokenizer.json --target 100000000 --context 64 --embed 128 \
  --rank 30 --epochs 5 --lr 0.05 --batch-size 32

nib dense-build --turbo turbo.bin --output dense-100m.bin --tokenizer tokenizer.json

nib dense-train --input shakespeare-200k.txt --output dense-100m.bin \
  --tokenizer tokenizer.json --init-turbo turbo.bin \
  --epochs 2 --max-samples 20000 --batch-size 128 --lr 0.02

nib dense-train --input shakespeare-200k.txt --output nib.bin \
  --tokenizer tokenizer.json --init-dense dense-100m.bin --hidden 10902 \
  --epochs 3 --max-samples 20000 --batch-size 128 --lr 0.01

Results vary because the trainer does not fix a random seed.

Benchmarks are from one development laptop CPU. Dense generation cost scales with length; 120 characters took about 11 seconds in CLI sampling (~90 ms/char). Turbo is the interactive choice; dense is the artifact for inspecting a real 90M-weight model.

Prompt behavior

Both generators use a fixed 64-character context. A short prompt is repeated to fill the context instead of being padded with spaces, which keeps the input closer to real text. A prompt longer than 64 characters is truncated from the left. Natural prompts of 64+ characters give the most coherent output.

Limitations

  • Character-level, not subword. No BPE tokenizer, no instruction tuning, no chat template.
  • Small corpus. 200 KB of Shakespeare is enough for style and structure, not general knowledge.
  • No validation split. Reported loss is training loss; overfitting is possible.
  • Fixed 64-character context. Longer prompts are truncated, not attended to.
  • Quantization after training. 4-bit storage is not trained with quantization-aware gradients.
  • CPU only. No GPU kernels, no SIMD intrinsics beyond what the compiler emits, no batched inference server.
  • Not a foundation model. Do not compare it to pretrained LLMs; it is a from-scratch educational and embeddable model.

Frequently asked model questions

Is the shipped model really trained from scratch?

Yes. Turbo starts from Xavier-random factors and learns from the Shakespeare file. Dense is expanded from that project's own Turbo factors, then fine-tuned with dense gradients. No external checkpoint is loaded.

Why is the dense file 45 MB rather than 90 MB?

Weights are stored at 4 bits each. 90M × 0.5 bytes is about 45 MB; row scales and biases add about 80 KB.

Why not keep 100M parameters?

A 100M dense model at 4 bits is 50,128,686 bytes, slightly over 50 MB. Pruning 1,212 hidden units lands at 45.12 MB while keeping the model fully dense. The 100M configuration is still available through dense-build.

Can it run on a GPU?

Not currently. The implementation uses ndarray on the CPU. GPU support would require a new backend and is outside the current scope.

Can I train on my own text?

Yes. Point --input at any UTF-8 text file and use a matching tokenizer path. A larger, cleaner corpus improves quality more than adding epochs.
