What you can do with Nib

Nib is not a chatbot. It is a small, trainable character model plus a complete toolkit around it. These are the concrete tasks it handles today, with the exact command or API for each one.

Pick the right model first

You want…UseWhy

1. Continue text in a learned style

The problem: you want offline, deterministic-ish text continuation without an API key, GPU, or Python stack.

# Fast model: 200 characters in well under a second
nib turbo-generate --model turbo.bin --tokenizer tokenizer.json \
  --seed "ROMEO: " --length 200 --temperature 0.7

# Dense model: slower, but every one of the 90M weights is used
nib dense-generate --model nib.bin --tokenizer tokenizer.json \
  --seed "First Citizen: Before we proceed any further, hear me speak." \
  --length 120 --temperature 0.7

Real output from the shipped nib.bin (temperature 0.7):

First Citizen: Before we proceed any further, hear me speak.

CORIOLANUS:
Au, I chole vile wishing hear ford fanit. Bubl as, no Rome.

COMINIUS:
I sull were your be somen:

It reproduces speaker labels, line breaks, and Elizabethan spelling patterns. It does not understand the plot. Longer, natural prompts produce better output than one-word seeds.

2. Train on your own text

The problem: you have a corpus — notes, lyrics, source code, logs, a novel — and want a model that mimics it.

# 1. Put UTF-8 text in a file, e.g. mydata.txt
# 2. Train a small readable CharLM (JSON, fast)
nib train --input mydata.txt --output model.json --tokenizer tokenizer.json \
  --context 12 --hidden 128 --embed 24 --epochs 40 --lr 0.1

# 3. Or train the compact Turbo model for better quality at ~1 MB
nib turbo-train --input mydata.txt --output turbo.bin --tokenizer tokenizer.json \
  --target 100000000 --context 64 --embed 128 --rank 30 \
  --epochs 5 --batch-size 32 --max-samples 50000

# 4. Or train a dense model from random weights (slow on CPU)
nib dense-train --input mydata.txt --output my-dense.bin --tokenizer tokenizer.json \
  --target 100000000 --epochs 1 --max-samples 2000 --batch-size 128 --lr 0.01
  • Use at least ~100 KB of clean text. More data helps more than more epochs.
  • Use a matching tokenizer. train and turbo-train build one from the corpus if the file is missing. Keep the tokenizer with the model.
  • Character-level means every character counts. Mixed encodings, HTML boilerplate, or binary junk become part of the vocabulary.
  • Validate by sampling, not just loss. The trainer reports training cross-entropy; there is no held-out split.

3. Build a next-character predictor or autocomplete

The problem: you need a tiny model that scores the next character given a short context, inside a Rust program.

use nib_rs::{dense, turbo, Tokenizer};

let tok = Tokenizer::load("tokenizer.json")?;
let mut model = dense::load_int4("nib.bin")?;
let context = model.config.context;

let mut ctx = turbo::context_from_seed(&tok, "Once upon a time", context);
let mut out = String::from("Once upon a time");
for _ in 0..40 {
    let probs = model.predict(&ctx);
    let next = turbo::sample(&probs, 0.7);
    out.push(tok.id_to_char.get(&next).copied().unwrap_or('?'));
    ctx.remove(0);
    ctx.push(next);
}
println!("{out}");

predict returns a probability vector over the 62-character vocabulary. Use argmax for deterministic completion or turbo::sample for creative continuation. The context is fixed at 64 characters; slide the window as you go.

4. Run a JSON API for any client

The problem: a website, script, or mobile app needs a simple HTTP endpoint.

nib serve --model nib.bin --tokenizer tokenizer.json --host 0.0.0.0 --port 8080
curl -X POST http://127.0.0.1:8080/api/generate \
  -H "content-type: application/json" \
  -d '{"prompt":"ROMEO: ","length":120,"temperature":0.7}'

The response is plain JSON with text, prompt, length, temperature, and ms. CORS is open, so a page on any origin can call it. This is a local endpoint by default; the hosted Pages UI has no backend. To get a public HTTPS URL, use a tunnel for a demo or deploy the binary, then open the UI with ?api=https://your-host. See HTTP API → What is the endpoint? for every step.

5. Put a generator on any website

The problem: you want a working demo on GitHub Pages, Netlify, Vercel, Cloudflare Pages, or an existing site, without a frontend build.

# Export the single-file UI
nib web-export --output index.html

# Host index.html anywhere static, then point it at the API
https://your-site.example/?api=https://your-nib-api.example
<iframe src="https://your-site.example/?api=https://your-nib-api.example"
        width="100%" height="760"
        style="border:0;border-radius:16px"
        title="nib-rs language model"></iframe>

The UI stores the endpoint in localStorage, checks /health, and shows the ready-made iframe snippet. Static hosting cannot run Rust, so the API lives on a separate VPS, Docker host, Render, Railway, Fly.io, or Cloud Run service.

6. Embed the model in a Rust application

The problem: you want generation in-process, with no server and no network hop.

[dependencies]
nib-rs = { git = "https://github.com/Vamshavardhan50/nib-ai.git" }
use nib_rs::{dense, Tokenizer};

let tok = Tokenizer::load("tokenizer.json")?;
let mut model = dense::load_int4("nib.bin")?;
let text = dense::generate_text(&mut model, &tok, "ROMEO: ", 120, 0.7);
println!("{text}");

The Rust API page covers training, quantization, pruning, low-rank models, vision, and the HTTP server. Dense loading needs roughly 400 MB of RAM; Turbo stays under about 20 MB.

7. Ship it with Docker or a single binary

The problem: you need a reproducible deployment with no runtime dependencies.

# Fast Turbo image
docker build -t nib-turbo .
docker run --rm -p 8080:8080 nib-turbo

# 90M dense image
docker build --build-arg MODEL=nib.bin -t nib-dense .
docker run --rm -p 8080:8080 --memory=1g nib-dense

The runtime image contains the nib binary, one model, and the tokenizer. See Deployment for systemd, Caddy, nginx, GitHub Pages, and platform-specific settings.

8. Classify images with the CNN

The problem: you want a from-scratch convolutional classifier for a small, controlled image set — shapes, colors, symbols, simple objects.

# manifest.txt: one "path label" pair per line
# data/red/01.png 0
# data/blue/01.png 1

nib vision-train --manifest manifest.txt --output vision.json \
  --image-size 16 --channels 3 --classes 2 --epochs 20 --batch-size 16 --lr 0.01

nib vision-predict --model vision.json --image data/red/02.png \
  --classes classes.txt

classes.txt is optional: one display name per line. The CNN resizes images, converts channels, normalizes pixels, and trains convolution, pooling, and the final linear layer with hand-written backprop. It is suitable for toy or narrow datasets, not ImageNet.

OCR is not part of this. The CNN returns one label for the whole image. It can classify a pre-cropped character, but it cannot find or read a line of text. The Vision & OCR guide has a measured digit example (95.33% on 300 held-out images), the single-glyph recipe, and the full list of OCR requirements.

9. Explore size and compression tradeoffs

The problem: you want to see exactly what fits in a size budget before committing to a training run.

# Turbo: logical shape vs stored factors vs file bytes
nib turbo-info --target 100000000 --tokenizer tokenizer.json

# Dense: exact parameters and 4-bit bytes for a hidden width
nib dense-info --hidden 10902 --tokenizer tokenizer.json

# Materialize a dense model, then prune and fine-tune it
nib dense-build --turbo turbo.bin --output dense-100m.bin --tokenizer tokenizer.json
nib dense-train --input shakespeare.txt --output nib.bin --tokenizer tokenizer.json \
  --init-dense dense-100m.bin --hidden 10902 \
  --epochs 3 --max-samples 20000 --batch-size 128 --lr 0.01

turbo-info and dense-info are instant and do not allocate the model. Use them to choose a shape, then train once. The Models & training page has the full size math and the 100B impossibility argument.

10. Learn or teach how a language model works

The problem: you want a complete, readable implementation instead of a framework call.

TopicFileWhat is hand-written
Tensors and indexingsrc/tensor.rsTensor1, Tensor2, Tensor4
Layerssrc/layers.rsLinear and embedding forward/backward
Text modelsrc/model.rsCharLM, tokenizer, trainer, sampling
Compressionsrc/turbo.rs, src/dense.rsLow-rank factors, int8, 4-bit, pruning
Visionsrc/vision.rsConv2d, max pooling, CNN backprop
Servingsrc/web.rsHTTP parsing, JSON API, CORS, UI

Every layer is a normal Rust struct with explicit gradients. Run cargo test to see shape, roundtrip, training, and HTTP tests. There is no autograd and no hidden framework magic to trace through.

What it cannot do

Set expectations before you build on it

The shipped models are character-level MLPs trained on 200 KB of Shakespeare. They continue text; they do not answer questions, follow instructions, browse, call tools, or hold a conversation. There is no attention, no BPE tokenizer, no chat template, and no world knowledge beyond the corpus.

  • No question answering or reasoning. “What is the capital of France?” is outside the training objective.
  • No long context. The window is 64 characters; longer prompts are truncated from the left.
  • No streaming or batching. One JSON response per request; generation is serialized.
  • No GPU backend. Everything runs on the CPU through ndarray.
  • No built-in auth, TLS, or rate limiting. Put a reverse proxy in front of a public instance.
  • No 100B model in 100 MB. That is physically impossible at any usable precision; Nib targets 90M weights in 45 MB.
