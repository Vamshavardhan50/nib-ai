Frequently asked questions

Direct answers about what Nib is, what it is not, how the sizes work, and why the model behaves the way it does.

Project and naming

What is Nib?

Nib (nib-rs) is a from-scratch Rust implementation of character-level language models and a small vision CNN. It includes training, quantization, a CLI, a Rust library, a zero-dependency HTTP API, and a browser UI. The shipped dense artifact has 90,004,008 independent weights in 45,117,066 bytes.

Why the name “Nib”?

A nib is the writing tip of a pen: small, precise, and the part that actually touches the page. It fits a project about compact models and generated text. The package is nib-rs, the binary is nib, and the library is nib_rs.

Is this the official Cactus project?

No. Nib is an independent implementation inspired by the goals of small, embeddable language models. References to Cactus or its Needle model in the README are context, not affiliation. All code and weights here are produced by this repository.

Did the project get renamed?

Yes. Earlier development used the name cactus-rs. The current name is Nib, and all package names, commands, UI titles, docs, and artifacts use it. The new repository is Vamshavardhan50/nib-ai.

From scratch and data

Is it really trained from scratch?

Yes. TurboLM starts from Xavier-random low-rank factors and trains on real text with hand-written forward and backward passes. DenseLM is expanded from this project's own Turbo factors, then fine-tuned with dense gradients. No external checkpoint, GGUF, or pretrained weight file is loaded.

What data was used?

The first 200,000 bytes of Tiny Shakespeare, a public-domain corpus of Shakespeare plays and poems. That is 7,554 lines and a 62-character vocabulary. The full corpus is about 1.1 MB; the shipped run used a 200 KB prefix so CPU training stayed practical.

Is the data mock or synthetic?

No. It is real public-domain text downloaded over HTTPS by get-data.ps1. The training windows are slices of that text; no labels or samples are fabricated.

Is there a validation split?

Not in the shipped run. Reported losses are training cross-entropy. Adding a held-out split is a good next step; the trainer already accepts arbitrary windows, so it is a small change to evaluate on a disjoint slice.

How long does training take?

On the development laptop CPU, dense fine-tuning runs at roughly 0.035 seconds per sample at batch 128, about 12 minutes per 20,000-window epoch. Three epochs is roughly 35–40 minutes. Turbo training is much faster; CharLM is seconds to minutes depending on size.

Model size and the 100B question

Why does the dense model have 90M parameters instead of 100M?

A 100M dense model at 4 bits is 50,128,686 bytes, slightly over 50 MB. Pruning 1,212 hidden units produces 90,004,008 parameters and a 45,117,066-byte file, comfortably under 50 MB. The 100M configuration is still available with dense-build or dense-train.

Can 100B parameters fit under 100 MB?

No. 100B weights at 1 bit per weight need about 12.5 GB. At 4 bits they need about 50 GB; at int8 about 100 GB; at f32 about 400 GB. This is an information-theoretic floor, not an implementation limitation. No compression scheme can put 100B independent weights in 100 MB.

How does Turbo fit a 100M shape in under 1 MB?

Turbo stores each large matrix as two thin factors, U·V, with rank 30. The logical dense shape is 100,009,068 parameters, but only 994,572 independent values are stored. It is a low-rank model of that shape, not a dense 100M-weight model. DenseLM is the artifact with 90M independent weights.

Is the 4-bit file still a “real” 90M model?

Yes. Every one of the 90,004,008 weights exists as a signed 4-bit value plus one f32 scale per row. Loading dequantizes them into f32 matrices. The storage is compressed; the network is dense.

What does 4-bit quantization cost in quality?

There is some loss because each row shares one scale and weights are rounded to 15 levels. The project quantizes after training, then reloads the artifact and checks predictions in tests. Fine-tuning before quantization keeps the loss small, but this is not quantization-aware training.

Quality and behavior

Why is the generated text sometimes garbled?

The model is a 90M-parameter character-level MLP trained on 200 KB of Shakespeare. It learns spelling, speaker labels, line breaks, and local style, not general language understanding. Short prompts are repeated to fill the 64-character context; longer natural prompts produce better output. Temperature also matters: very high values increase noise.

Can it answer questions or follow instructions?

No. It is not instruction-tuned and has no chat template. It continues text in the style of its corpus. Asking “What is the capital of France?” is outside its training objective.

Why character-level instead of BPE?

Character-level tokenization is simple, deterministic, and has a tiny vocabulary (62 tokens here). It makes the whole pipeline readable and keeps the embedding table small. A BPE tokenizer would improve long-range efficiency but add substantial complexity.

Why an MLP instead of a transformer?

The goal is a small, fast, from-scratch CPU model with a fully understandable training loop. A fixed-context MLP is much simpler than attention and still learns local character patterns. Transformers are a possible future direction, not a current feature.

Can I train on my own text?

Yes. Point --input at any UTF-8 text file. Use a matching tokenizer path; the tokenizer is built from the corpus for CharLM and Turbo. More clean data usually helps more than more epochs.

Can I use the full 1.1 MB Shakespeare corpus?

Yes. Run get-data.ps1 and train on the full file. Expect longer training and somewhat better coverage. The shipped 200 KB prefix was a deliberate speed/quality tradeoff.

Performance

Why is dense generation slow?

Every generated character runs a forward pass through 90M weights on the CPU: about 89M multiply-adds in fc1 alone. A 20-character HTTP request takes about 1.7 seconds; 120 characters take about 11 seconds. Turbo is roughly two orders of magnitude cheaper per character.

How fast is Turbo?

Turbo 200-character generation takes 0.15 s (150 ms) on the development CPU. It is the right choice for an interactive demo.

How much RAM does it need?

Dense loads 90M f32 weights, about 360 MB, plus activations and runtime overhead; allow about 400 MB and use a 1 GB container limit. Turbo stays under about 20 MB. Training needs more than inference because it keeps gradients and intermediate matrices.

Can it use a GPU?

Not currently. The implementation uses ndarray on the CPU. GPU support would require a new backend, kernels, and memory management; it is outside the current scope.

Vision and OCR

Can Nib read text from an image?

No. Nib has no OCR engine. The vision model is a single-label image classifier: one image in, one class and one confidence out. It cannot detect text, segment lines, or return a string of characters. It can classify a pre-cropped character if you train it on glyphs and do the cropping yourself. For real OCR use Tesseract, PaddleOCR, EasyOCR, docTR, or a cloud vision API. Full explanation and the single-glyph recipe: Vision & OCR.

How accurate is the vision model?

On a real 10-class handwritten-digit test — 1,497 training images and 300 held-out images at 16×16 grayscale — it reached 95.33% (286/300) after 30 epochs in 13.5 seconds. That number is specific to that dataset and input size. Accuracy on your images depends on how many labeled examples you provide, class balance, and how closely prediction images match the training framing.

Does nib serve expose the vision model?

No. The HTTP server loads only CTURBO01 and CDENSE4 text models. Vision is available through nib vision-train, nib vision-predict, and the Rust API. See Vision limits.

API and deployment

What is the API endpoint?

There is no public endpoint hosted for you. The Pages UI and docs are static. Start the server locally with nib serve --model nib.bin --tokenizer tokenizer.json --host 127.0.0.1 --port 8080 and use http://127.0.0.1:8080. After deploying, the base URL is your HTTPS host, for example https://api.example.com, and generation is always POST {base}/api/generate. The full walkthrough — local, tunnel, public host, UI connection, and troubleshooting — is in HTTP API → What is the endpoint?.

Does serve work with both models?

Yes. It reads the first eight bytes and dispatches to the Turbo int8 or dense int4 loader. The HTTP endpoints, UI, CORS behavior, and response schema are identical.

Can I host everything on GitHub Pages?

You can host the UI and this documentation site on Pages. Pages cannot execute Rust, so the API must run on a VPS, Docker host, Render, Railway, Fly.io, Cloud Run, or similar. Point the static UI at the API with ?api=https://your-api-host.

Is there authentication or TLS?

Not in the built-in server. Put it behind Caddy, nginx, a cloud load balancer, or a platform gateway for TLS, auth, rate limiting, and logging. CORS is intentionally open (*) so static demos can call the API.

Can I stream tokens?

No. /api/generate returns the full text in one JSON response after generation completes. Streaming would require a different response format and incremental decoding.

Can I embed the UI on my website?

Yes. Run nib web-export, host the HTML anywhere, and embed it with an iframe whose src includes ?api=https://your-api-host. The UI also shows a ready-made snippet.

Does it work offline?

Yes. The binary, model, tokenizer, and UI have no runtime network dependencies. Only the optional data downloader needs the internet.

Licensing and contributing

What license is the code under?

Apache-2.0. You can use, modify, and distribute it, including commercially, provided you keep the license and notices. The Shakespeare corpus is public domain.

Can I use the trained weights commercially?

The weights are generated by this project from public-domain text. Apache-2.0 covers the code; treat the weights as your own artifacts. As always, verify that your own training data and use case comply with applicable law and licenses.

How can I contribute?

Open an issue or pull request on GitHub. Run cargo test before sending changes. Useful directions include a validation split, larger corpora, a BPE tokenizer, SIMD kernels, streaming responses, and deployment examples.

Why is the binary about 3 MB?

It includes Rust's standard library, ndarray, serde, clap, and the image decoder, with LTO, one codegen unit, abort-on-panic, and symbol stripping. That is small for a complete trainer, server, and image pipeline, but not a microcontroller binary.

Known limitations

  • No validation split or held-out benchmark in the shipped run.
  • Character-level only; no BPE or subword tokenizer.
  • Fixed 64-character context; no attention or long-range memory.
  • CPU-only, single-threaded generation, no batching.
  • No streaming, authentication, TLS, or rate limiting in the server.
  • 4-bit quantization happens after training, not during it.
  • The model is a small Shakespeare-style character model, not a general assistant.
  • Training does not fix a random seed, so reproduced runs differ slightly.
